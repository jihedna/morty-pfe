# Scoring and ML Design

The project contains several distinct decision-support systems; they should not be described as one matching algorithm.

## Client-to-agent compatibility

Each available agent is evaluated against a client search request using explainable weighted criteria:

| Factor | Weight |
|---|---:|
| Requested property type matches agent expertise | 30% |
| Preferred city matches agent territory | 30% |
| Client budget overlaps agent budget range | 25% |
| Agent is available | 15% |

Matched weights produce a 0-100 compatibility score. Results are sorted by score and include factor-level explanations. This is deterministic business logic, not a trained model.

## Lead scoring

Search requests receive a 0-100 qualification score based on budget completeness, location specificity, urgency, notes/status, and recency. Labels are Hot (`>=70`), Warm (`>=45`), and Cold (`<45`). This helps agents prioritize; it does not guarantee conversion.

## Property recommendation

The recommender combines content-based property features with weighted user-interaction signals. Training creates a versioned artifact and metadata. Inference excludes unsuitable/unavailable items and falls back to deterministic ranking when no usable artifact or interaction history exists.

## Price estimation

Separate sale and rent regression pipelines train from property attributes. Inference returns an estimate and supporting range/metadata. If a model is unavailable, the service uses comparable median price per square metre by location/type.

## Lead-conversion prediction

A classification pipeline estimates conversion likelihood for agent workflows. When an artifact is unavailable or data is insufficient, a rule-based heuristic uses budget, location, engagement, and urgency signals. Raw conversion probabilities are not intended for client display.

## Governance

Model artifacts, metrics, comparisons, and cards are generated by `backend/ml/training/` and loaded through the model registry. Managers can inspect model status/metrics through `/api/v1/ml/models`. Retraining is a manual backend operation; there is no in-app training endpoint.
